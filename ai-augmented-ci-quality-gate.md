# AI-Augmented CI Quality Gate

**A Case Study in Governed, Auditable AI Assistance for Release Decisions**

*Prepared by Ashok — QA Automation Architect*
*Built on top of an existing Playwright/pytest automation framework and GitHub Actions CI pipeline*

---

## Executive Summary

Test suites fail for many reasons, and only some of them mean the product is broken. After every CI run, someone has to work through each failure and decide: is this a real defect, or is it the framework, test data, or environment getting in the way — and, either way, is this release safe to ship? That triage work is repetitive, time-consuming, and inconsistent between engineers. This project automates the repetitive parts of that workflow while deliberately keeping the release decision itself out of the AI's hands.

The system is built as three independent, sequentially-dependent stages on top of an existing Playwright automation repository: Part 1 imports and preserves the factual record of what happened in CI; Part 2 uses retrieval-augmented generation (RAG) with a large language model to propose an advisory root-cause classification for each failure; Part 3 applies a deterministic, versioned rules engine — combined with explicit, evidence-backed engineer review — to produce the final **GO / REVIEW_REQUIRED / NO_GO** recommendation. The AI never decides the release outcome. It proposes; a rules engine and a human confirm.

## 1. Background and Problem

The underlying Playwright automation repository runs a suite of UI, API, and database tests in GitHub Actions on every change, producing JUnit and Allure results as build artifacts. As the suite grows, so does the volume of failures that need manual review before every release: some are genuine product defects, others are framework flakiness, stale test data, or environment issues that have nothing to do with the product itself.

Two problems compound here. First, manually reading through failure logs and stack traces to categorize each failure does not scale as the suite grows. Second, and more importantly, simply handing that categorization to an LLM and trusting its verdict is not an acceptable substitute for a real release decision — especially in a regulated, BFSI-adjacent environment where every release decision needs to be explainable and auditable after the fact. The design goal was therefore not "automate the decision" but "accelerate the evidence-gathering and triage work, while keeping the actual decision deterministic, reviewable, and owned by engineers."

## 2. Design Philosophy

The architecture is built around one governing principle: **facts, AI opinions, and decisions are three different things, and the system never lets them blur together.**

- **Facts** — what actually happened in CI, imported once from GitHub Actions and never altered. Part 1 produces this and only this.
- **AI opinion** — an advisory classification and independent review generated by Gemini in Part 2, always clearly labeled as a proposal, always schema-validated and cited against real evidence, and never treated as ground truth.
- **Decision** — produced only by Part 3's deterministic rules engine plus explicit, evidence-backed engineer review. No LLM call happens at this stage.

A second theme running through all three parts is **append-only auditability**. Nothing is silently overwritten: every import, AI assessment, engineer review, and gate evaluation is persisted with fingerprints tying it to the exact inputs that produced it. If the underlying facts, knowledge base, or policy change, the system creates a new record and marks the old one stale rather than mutating history. This is the same instinct that governs financial and compliance systems, and it is a deliberate design choice rather than an accident of the schema.

The third theme is **cost- and risk-consciousness by default**: no cloud call happens unless explicitly enabled, every cloud request is previewable before it is sent, evidence is sanitized on a best-effort basis, and the whole pipeline runs at effectively zero infrastructure cost using SQLite and a free-tier LLM.

## 3. Three-Part Architecture

Each part is an independent extension of the last, added through its own versioned database migration, so earlier factual data and behavior are never disturbed by later parts.

### Part 1 — Evidence, History, and Factual Reporting

Part 1 is a read-only, local tool that pulls completed workflow runs from GitHub Actions, downloads their JUnit and Allure artifacts, and reconciles them into a single factual record per test execution. It does not run tests, change workflows, post comments, diagnose causes, or block anything — it only observes and records.

- **Ingestion** — paginated, retried GitHub API calls; bounded artifact downloads (512 MiB compressed, 1 GiB expanded, 20,000-file limit) with checksum verification and protection against zip-traversal and unsafe file types.
- **Reconciliation** — JUnit is treated as the authoritative source of observed outcomes; Allure data is matched in where it can be tied to a JUnit record with a unique, non-ambiguous identity. Anything that cannot be matched with confidence is retained as unassociated evidence and explicitly flagged — never silently guessed.
- **Storage model** — a normalized SQLite schema (`workflow_runs → jobs → test_results → sources/evidence`) with foreign-key and trigger-enforced integrity, so a result can never be linked to the wrong job or an orphaned run.
- **Output** — a local HTML/JSON execution report containing only observed facts. No AI verdict exists yet at this stage — the report deliberately shows `NOT_EVALUATED` rather than fabricating a recommendation it cannot support.

### Part 2 — RAG-Assisted Advisory Classification

Part 2 adds an advisory layer on top of the factual record, using retrieval-augmented generation with Gemini to propose a root cause for each failure — without ever presenting that proposal as confirmed.

- **Retrieval** — deterministic lexical matching (pytest identity, normalized error signatures, keyword overlap) against a small, curated, engineer-reviewed known-issues library. A vector database was deliberately not used — the knowledge base is small enough that a transparent, debuggable matching algorithm is the right tool, not a heavier one.
- **Two-role assessment** — for each failure, a classifier proposes a category and a second, independent reviewer assesses the same evidence blind — without seeing the classifier's answer. A third comparison call checks the two assessments against each other and the original evidence, and can only return "insufficient evidence" rather than a confident verdict if either underlying assessment was itself uncertain.
- **Validation and audit** — every model response is schema-validated, checked for citations against evidence actually supplied, and persisted with content fingerprints (prompt, schema, knowledge base version, evidence state). Any change to those inputs produces a new analysis rather than overwriting the old one.
- **Cost and safety boundaries** — cloud calls are disabled by default, previewable before being sent, capped per command, and never include raw screenshots, traces, or full archives — only sanitized text evidence.

### Part 3 — Deterministic Release Advisory

Part 3 is where the actual GO / REVIEW_REQUIRED / NO_GO recommendation is produced — and it makes no LLM call at all. It combines the Part 1 facts, the Part 2 proposals, and explicit engineer review through a pure, versioned rules engine.

| Situation | Outcome |
|---|---|
| Full verified coverage, all required behavior passes, no unresolved findings | GO |
| Verified accepted known issue with reason, reviewer, and expiry; all else satisfied | GO with comments |
| Framework, test-data, or environment failure, not yet manually checked | REVIEW_REQUIRED |
| New engineer-confirmed product defect on a smoke test | NO_GO |
| Engineer-confirmed critical/high defect elsewhere | NO_GO |
| Unknown cause or missing coverage, without a resolving engineer review | REVIEW_REQUIRED |

- **Human-in-the-loop exceptions** — an engineer can record a manual pass, accept a known issue, or confirm a defect — each requires reviewer identity, reasoning, supporting evidence, and (where relevant) an expiry date. Reviews are append-only: correcting one means superseding it with a new record, never editing history.
- **Coverage verification** — rather than inferring that "all observed tests passed" proves full coverage, an engineer explicitly reviews and confirms an expected-test inventory against the real pytest collection and smoke markers before REVIEW_REQUIRED can become GO.
- **Snapshotted evaluations** — every decision is stored with the exact policy version and input fingerprints that produced it. A stale saved GO is automatically shown as REVIEW_REQUIRED the moment relevant facts, reviews, or policy change underneath it.

## 4. Technology Stack

| Layer | Choice | Why |
|---|---|---|
| Language / core | Python, Pydantic, class-based services | Matches existing automation stack; strict schemas everywhere |
| Storage | SQLite (append-only audit tables) | Zero infrastructure cost; real relational integrity; single-file portability |
| LLM | Gemini, free-tier, explicit opt-in | No default cost; structured JSON output; easy to swap providers |
| Retrieval | Deterministic lexical matching | Small curated knowledge base; transparent and debuggable, no vector DB needed |
| CI integration | GitHub Actions REST API | Reads existing workflow artifacts without modifying the test pipeline |
| Reporting | Jinja2 → escaped local HTML/JSON | No external resources or scripts; safe to open and share offline |
| Quality tooling | pytest (unit / db / integration), Ruff | Mirrors the discipline of the underlying Playwright framework |

## 5. Testing Strategy

The analyser is tested with the same rigor it applies to the product under test: a unit layer covering configuration, models, parsers, and transport in isolation; a database layer exercising real SQLite constraints, triggers, and migrations rather than mocks; and an integration layer running the complete offline import-and-report pipeline, including reruns and repeated imports, to confirm idempotency. Each part also ships an isolated synthetic demo script, so the full pipeline — including example GO, REVIEW_REQUIRED, and NO_GO outcomes — can be demonstrated without any live GitHub or Gemini credentials and without touching real project history.

## 6. Why This Design Matters

This project is deliberately not "a chatbot that reads test logs." It is an attempt to answer a harder and more realistic question: how should AI actually be integrated into a release-quality process in a way a QA organization, and its auditors, could actually trust?

- **Governed AI, not autonomous AI** — the system demonstrates a concrete pattern — LLM proposes, deterministic rules and humans decide — that generalizes well beyond QA to any regulated decision workflow.
- **Production-grade guardrails** — schema validation, citation checking, blind independent review, and fingerprint-based caching are the same techniques used in serious LLM evaluation pipelines, applied here to a real operational problem.
- **Full auditability** — append-only history, versioned policy, and fingerprinted evaluations mean any past decision can be explained and reproduced — a real requirement in BFSI-adjacent environments.
- **Built on real infrastructure** — the system extends an existing, production Playwright/pytest framework with 54 tests and a working CI pipeline, rather than being a synthetic toy example.
- **Cost-conscious by construction** — SQLite, free-tier LLM access, and explicit opt-in cloud calls mean the entire system runs at effectively zero infrastructure cost — a deliberate architectural constraint, not a limitation.
